# 01. 项目初衷、核心愿景与架构哲学

---

## 一、 为什么要做“WASM 工厂”？

在现代软件工程中，系统面临着高度异构的运行环境：
- 前端有浏览器（Chrome / Safari / Firefox）、移动端（Flutter / React Native）；
- 后端有 Node.js、Java、Go、Python、C#（.NET）以及各种云原生微服务；
- 边缘侧有 Cloudflare Workers、Fastly Compute、Envoy 网关插件。

过去，为了在不同端实现一套核心算法（例如：复杂的加密算法、定制编解码器、数据解析引擎、业务规则计算器），企业往往需要用多种语言分别实现一遍。这种方式带来了巨大的维护成本：
1. **逻辑一致性难以保障**：语言特性的细微差异（如浮点精度、字符串编码、整数溢出行为）极易引发跨端逻辑不一致；
2. **重复造轮子**：每个语言栈都要维护测试套件与修复补丁；
3. **性能瓶颈**：解释型或动态语言（如 JS/Python）在处理 CPU 密集型任务时性能不足。

**WebAssembly (WASM) 为此提供了终极解法**。
构建“WASM 工厂”的初衷，就是**建立一个统一的代码生产流水线：用系统级或强类型语言编写核心逻辑，编译出纯净的 WebAssembly 字节码，随后分发嵌入到任何支持 WASM 虚拟机的宿主环境中**。

---

## 二、 为什么选择 Rust 与 AssemblyScript 双技术栈？

在建设 WASM 工厂之初，我们深入对比了社区中最具代表性的两套语言方案，并决定同时将其纳入工厂体系：

### 1. Rust —— 工业级、极致性能与安全基石
- **零运行时 GC**：基于 RAII 与所有权系统，内存开销极其精简，无垃圾回收带来的毫秒级停顿（Stop-the-world），执行时延高度可预测；
- **生态庞大**：crates.io 拥有全行业最丰富的高性能密码学、图像视频处理、语法分析器、数据结构库；
- **行业标杆**：Rust 是 WebAssembly 标准委员会的第一公民（Tier 1），具有最前沿的技术规范兼容性。

### 2. AssemblyScript —— 前端与全栈团队的极速敏捷通道
- **学习曲线平缓**：基于 TypeScript 静态子集，前端工程师几乎零门槛上手；
- **开发效率极高**：编译速度快，非常适合快速构建算法原型、轻量级业务计算逻辑。

通过在工厂中同时沉淀 **Rust** 与 **AssemblyScript**，我们构建了“兼顾极致性能与敏捷开发”的双轮驱动体系。

## 三、 核心架构哲学：彻底告别 JS 胶水，追求“纯净的单一 `.wasm` 文件”

这是本项目最重要的设计觉醒与分水岭。

### 1. 社区常规方案的局限性
在初期的探索中，社区主流工具（如 `wasm-pack` 的 bundler/web 目标，或 `asc` 的默认编译）都会打包生成一系列 `.js` 辅助胶水文件（Glue Code，如 `rs_wasm.js`、`release.js`）。
这些胶水代码虽然在纯前端打包（Webpack / Vite）场景下很方便，但**带来了严重的生态壁垒**：
- 它将 WASM 与 JavaScript 宿主深度绑定；
- 如果我们要把同一个 WASM 模块放入 Java (Wasmer)、Python (wasmtime)、C#、Go (wazero) 或 C++ 宿主中，这些 JS 胶水文件完全无法运行，甚至会成为负担。

### 2. 我们的坚持：Host-Agnostic（宿主无关性）
我们的原则是：
> **产出端极简，消费端自洽。**
> 工厂输出给外部世界的，必须是且仅是一个孤立、纯净、无任何语言绑定的标准二进制文件：`rs.wasm` 和 `ts.wasm`。

- **产出端**：不管是 Rust 还是 AssemblyScript，都通过标准 C-ABI 约定输出纯 `.wasm` 字节码；
- **消费端**：加载、实例化（Instantiate）、内存分配、指针解析与字符串 UTF-8 编解码的逻辑，作为各宿主框架的**基础设施（Infrastructure）**来实现。

无论宿主是 **Node.js、浏览器、Java、Python、Go、C# 还是 Flutter**，只要遵循统一的标准内存交互规范，就能拿来即用！
